Technical survey / revised edition

GLIM + lidar_localization_ros2 と MOLA の比較調査

同一rosbagによる地図作成・ローカリゼーション試験、計算資源、Unitree Go2／Jetson搭載候補の整理

調査日：2026-08-11　対象：Ubuntu 22.04 / ROS 2 Humble / Livox MID-360

1. 結論

現時点の実測を優先すると、GLIMで地図を作成し、lidar_localization_ros2で既知地図ローカリゼーションを行う構成が第一候補である。

第一候補

デスクトップPC：GLIMで高品質地図作成
ロボット：lidar_localization_ros2 / NDT_OMPで運用し、計算余裕があればv1.2のLiDAR–IMU密結合経路を比較する。

MOLAの現時点の評価

採用保留
同じデータから作った地図に同じデータを再入力しても位置推定が地図外へ逸脱し、開始地点に戻れなかった。原因を切り分けるまでは実機候補にしない。

軽量化を優先する場合

平坦な単一フロアなら、GLIMの3D地図から2D地図を作り、Nav2 AMCLでmap → odomを推定する構成が最も軽量で扱いやすい。

高い追従性を優先する場合

LiDAR、IMU、scan-to-scan、scan-to-mapを同時最適化する密結合方式が有利。OSSではlidar_localization_ros2 v1.2を先に評価し、商用導入可能ならGLILも候補になる。

重要： FAST-LIO2は高速なLiDAR–IMUオドメトリ／マッピングであり、単体では事前に作ったGLIM地図に対する絶対ローカリゼーションではない。FAST-LIO2だけでは長時間のmap → odom補正を保証できない。

推奨順位

順位構成判断主な理由
1GLIM地図 + lidar_localization_ros2 / NDT_OMP継続評価今回の同一rosbagで完走。CPUのみで動作し、Humble・Nav2・PCD地図との接続が容易。
2GLIM地図 + lidar_localization_ros2 v1.2 密結合経路比較試験scan-to-scan、scan-to-map、IMUを固定遅延因子グラフで統合。NDTより高負荷だが、地図欠損や急運動への耐性が期待できる。
3GLIM 3D地図 → 2D地図 + Nav2 AMCL平坦面なら推奨計算負荷が小さい。単一フロアの巡回には実用性が高い。
4MOLA + ループ閉じ込み済み地図 + MOLA Localization原因確認後CPU実装で柔軟だが、今回の構成では自己データ再生でも地図外へ逸脱した。
5GLIL契約可能なら候補密結合方式として強力。ただしクローズドソースで有償契約が必要。

2. 今回の実測結果をどう評価するか

今回の試験では、両構成とも同じrosbagを使って地図を作成し、同じrosbagをもう一度再生してローカリゼーションを行った。

構成地図作成ローカリゼーション結果現時点の評価
GLIM + lidar_localization_ros2 GLIMによる3D地図 最後まで追従 現在のデータ・設定・環境に対して成立した基準構成。
MOLAで完結 MOLAで地図作成 途中で地図外へ逸脱し、元の開始地点へ戻れなかった プロセス停止ではなく、幾何学的な位置推定破綻。原因解明まで採用保留。
この試験は実運用より有利： 地図作成時とまったく同じ観測を再入力しているため、環境変化、家具移動、季節差、別走行軌跡といった難しさがない。この条件でも逸脱するなら、現在のMOLA構成をそのままGo2へ載せるのは危険である。

一方で、この結果だけから「MOLAのアルゴリズム全体が弱い」とは断定できない。地図がループ閉じ込み前だった、simplemap → mm変換条件が不適切だった、SLAM時とLocalization時の前処理が一致していなかった、という可能性を分離する必要がある。

3. SLAM・オドメトリ・ローカリゼーションの役割

SLAM／地図作成

未知環境を移動しながら軌跡と地図を同時推定する。ループ閉じ込みや全体最適化によって、累積ドリフトを地図全体へ配分する。

オドメトリ

直近の移動量を高周期で推定する。局所的には滑らかだが、絶対基準がないため長時間ではドリフトする。

既知地図ローカリゼーション

固定された事前地図に現在スキャンを照合し、地図上の絶対位置を推定する。Nav2では通常map → odom補正を担う。

GLIMで地図作成高性能PC、GPU、全体最適化
地図を配備PCD／PLY、必要なら2D地図も生成
ロボットで位置推定NDT／GICP／密結合方式、Nav2へ接続

地図作成とロボット運用で同じアルゴリズムを使う必要はない。むしろ、地図作成は精度優先、運用時は計算量と復旧性を優先して分ける方が合理的である。

4. アルゴリズム比較

4.1 GLIMによる地図作成

GLIMはLiDAR／深度点群とIMUを因子グラフ上で統合する3D SLAMである。オドメトリ部では固定遅延スムージングとキーフレーム間の点群マッチングを使い、地図全体ではサブマップ間の登録誤差を直接最小化する。

  • IMU preintegrationとGPU加速GICP／VGICP因子を利用
  • 過去数秒分の状態を残して再線形化する固定遅延スムージング
  • サブマップ間の小さな重なりも登録制約として利用
  • iSAM2による増分因子グラフ最適化
  • 一時的な点群縮退や欠損に比較的強いが、CPU・GPU負荷は大きい

4.2 lidar_localization_ros2 / NDT_OMP

NDTは地図をボクセルに分け、各ボクセル内の点分布を正規分布として表し、現在スキャンがその分布へ合う姿勢を反復計算する。NDT_OMPはCPU並列化された実装である。

姿勢予測前回姿勢、twist、odom、IMU
scan-to-map NDT既知PCD／PLY地図へ位置合わせ
品質判定と出力スコア、収束、map → odom
  • GICPより大きめの初期誤差を吸収しやすい場合がある
  • CPUのみで動作し、OpenMPのスレッド数を調整できる
  • 廊下、平面、反復構造では局所解へ誤収束する可能性がある
  • 一度追従を失うと、通常の局所NDTだけでは自動復帰が難しい

現在のlidar_localization_ros2 v1.2.0には、従来のNDT／GICPに加え、IMU preintegration、scan-to-scan GICP、scan-to-prior-map GICPを固定遅延因子グラフで同時最適化する経路が追加されている。これはNDT_OMPとは別アルゴリズムであり、計算負荷と頑健性を別に測定する必要がある。

4.3 MOLAの地図作成とローカリゼーション

MOLA-LOはICP系のscan-to-local-map推定を中核とし、速度もICP内部で同時推定する柔軟なパイプライン型システムである。地図は観測と姿勢を保持するsimplemapを基礎表現とし、後処理で用途別のmetric mapへ変換できる。

MOLA-LIO／LOrosbagから*.simplemap生成
mola-sm-lc-cliオフラインのループ検出・軌跡補正
sm2mm補正後の*.mm地図を生成
  • GICP／ICP、適応的対応距離、ロバストカーネル、品質評価を組み合わせる
  • per-point timestampを使ったdeskewに対応
  • 現在のMOLA 3.0系ではIMUによるdeskew、重力方向補正、状態推定Smootherを選択可能
  • Localization-onlyでは固定地図に対してLOパイプラインを動かすため、SLAM時のように地図を追加して追従を救済できない
バージョンを固定して比較する： 2026年8月時点の公式資料はMOLA v3.0.0で、Localization-only、フレームdrop、地図公開、use_state_estimatorなどに修正・追加が入っている。今回試したMOLAのバージョンが異なる場合は、同じ設定名でも挙動が違う可能性があるため、パッケージバージョンとGit commitを試験記録へ残す。

5. MOLAが同一rosbagでも逸脱した原因候補

今回のMOLA未完走はクラッシュではなく、位置推定が途中から誤った地図座標を追い、地図外へ出たまま元の開始地点へ戻らなかったという追従失敗である。

原因候補の優先順位

  1. 地図にループ閉じ込みが反映されていない
    SLAM軌跡自体が閉じていなければ、開始地点と帰着地点が別の位置として地図化される。MOLA公式手順では、mola-sm-lc-cliの後にsm2mmを行う。
  2. SLAM時とLocalization-only時の性質の違い
    SLAM中は直近観測を地図へ追加できる。Localization-onlyでは固定地図との対応が必要なため、一度予測が外れると別の壁や廊下へGICPが誤収束しやすい。
  3. IMUの利用経路または時刻同期が不十分
    deskewだけでは姿勢状態を強く拘束しない構成がある。MID-360のpoint timestamp、IMU timestamp、外部姿勢、TFの時間関係を確認する必要がある。
  4. simplemap → mm変換でローカリゼーション用地図が変質
    voxelサイズ、キーフレーム採用、view direction、距離フィルタによって、SLAM内部で使えた局所形状が失われる可能性がある。
  5. 近距離の身体・ロボット点が入力された
    LiDARと共に動く身体やGo2本体は、環境地図と一致しない。SLAMとLocalizationで最小距離や自己領域除去を一致させる必要がある。
  6. 悪いICP解を棄却せず更新した
    overlap、quality、対応点数の閾値が緩いと、誤った解が次フレームの初期値になり、連鎖的に地図外へ進む。

FAST-LIO2論文とGo2記事が違って見える理由

FAST-LIO2論文ではARM上で平均5.23 ms/scanだが、TechShareのGo2記事ではOrin NXのCPUのみでは計算力不足と記載されている。これは矛盾ではなく、試験全体の条件差と考えるべきである。

  • 論文は位置合わせに756点/scanを使用
  • ROS 2移植、DDS、Docker、Livoxドライバ、RVizを含む負荷は論文のコア処理時間と異なる
  • MID-360の入力点数、voxelサイズ、scan frequency、IMU同期条件が異なる
  • Jetsonの電力モード、CPUクロック、冷却、サーマルスロットリングが影響する
  • Go2上でNavigation、認識、通信ノードとCPUを共有する
TOPS値に注意： NDT_OMP、MOLA、FAST-LIO2の公式実装は主にCPUアルゴリズムである。JetsonのAI TOPSが高くても、そのままscan matchingが速くなるわけではない。CPUコア性能、メモリ帯域、冷却、スレッド競合を測る必要がある。

7. Jetson／ロボット搭載時の推奨構成

NVIDIA公式仕様では、Orin Nano Superは6コアArm CPU、8 GBメモリ、7–25 W、Orin NXは最大16 GB・10–40 W級である。ただし下表のローカリゼーション適合性は公開ベンチマークではなく、今回の用途に対する工学的な選定目安である。

構成最低検証ライン実運用の推奨備考
2D AMCL4コアARM、4–8 GBOrin Nano 8 GBで十分な可能性が高い平坦面限定。3D点群は障害物検出に残せる。
NDT_OMP 3D localizationOrin Nano 8 GBで5 Hzから測定Orin NX 16 GB複数スレッドを使うため、他ノードとのCPU競合に注意。

GLIL GPU版CUDA対応Jetsonで互換性確認Orin NX 16 GB以上契約・対応CUDA・ROSディストリビューションを確認。
GLIMマッピングJetson上は限定試験x86デスクトップ + NVIDIA GPU + 16–32 GB RAM地図作成をロボット本体で行わない運用が合理的。

10 Hz MID-360での合格基準

  • 1倍速rosbagを最後まで再生して、入力キューが増え続けない
  • 平均処理時間 50 ms/scan以下、p95 80 ms/scan以下を目安にする
  • 100 ms超過が連続せず、姿勢出力の有効率が95%以上
  • CPUとメモリに20–30%の余裕を残す
  • 温度上昇後もクロック低下で性能が崩れない
  • RVizと高密度debug点群を止めても同じ精度が出る

最初に試す軽量化設定

  • ローカリゼーション入力を3,000–5,000点/scan程度から開始
  • 更新周期を5 Hzから開始し、余裕を確認して10 Hzへ上げる
  • 屋内voxelサイズを0.25–0.5 mから比較
  • 既知姿勢周辺だけ地図をcropし、半径30–50 mから調整
  • subscription queue depthを1にして古い点群をためない
  • Releaseビルド、RViz停止、debug publish停止

8. 追加候補の評価

8.1 lidar_localization_ros2 v1.2 密結合経路

最初に追加比較すべき候補である。現在使っているパッケージ内で、scan-to-scan、scan-to-map、IMUを同時最適化できるため、新しいシステム一式へ移行するより比較コストが小さい。Humble互換は維持されているが、プロジェクトの主対象はJazzyであり、Jetson + MID-360実機は別途測定が必要である。

8.2 SMALL_GICP／SMALL_VGICP

small_gicpはCPU上で点群登録と前処理を並列化した実装で、GPUを含まない。NDT_OMPとの比較候補として有効だが、GICPは良い初期値と地図重なりに依存しやすいため、今回のMOLAのような逸脱を自動的に解決するわけではない。

8.3 GLIL

LiDAR–IMU、scan-to-scan、scan-to-mapを滑動窓因子グラフで密結合し、地図境界や一時的な未地図領域でもオドメトリへ移行して復帰できることを狙った方式である。アルゴリズムとしては有力だが、公式実装はクローズドソースで有償契約が必要である。

8.4 Autoware ndt_scan_matcher

大規模PCD地図、Monte Carlo初期化、スコア・実行時間diagnostics、動的地図ロード、GNSS regularizationなどが必要なら有力である。ただしAutowareの依存関係とフレーム設計はGo2には大きく、現在のlidar_localization_ros2より導入コストが高い。

8.5 GLIM地図 → 2D地図 → Nav2 AMCL

単一フロア中心の巡回では最も現実的な軽量候補である。3D姿勢や階段、複数階を単一地図として扱う用途には向かないが、Nav2運用を優先するなら別枠で必ず比較する価値がある。

8.6 FAST-LIO2 + 低周期地図マッチャ

FAST-LIO2で高周期のodom → base_linkを作り、NDT／GICPを低周期で実行してmap → odomを補正する構成は成立する。ただし二つの推定器のTF責任、時刻、共分散、リセット処理を設計する必要がある。新規に疎結合システムを組むより、まずlidar_localization_ros2 v1.2の密結合経路を評価する方が近道である。

9. 公平な比較試験の設計

同じrosbagを使うだけでは、地図品質とローカライザ性能が混ざる。次の4条件を作ると、どちらが原因か分離できる。

CMOLA + loop closure後にPCD出力lidar_localization_ros2MOLA地図品質とNDTの相性を評価。
DMOLA + loop closure後のMM地図MOLA LocalizationMOLAの正式パイプライン全体を評価。
変換時の注意： A〜Dで点群密度、座標原点、重力方向、地図の高さ範囲、自己領域除去、最小／最大距離をできるだけ一致させる。形式変換だけで点群密度が大きく変わると、公平なlocalizer比較にならない。

記録する指標

分類指標合格判定例
追従性最後まで生存、地図内維持、有効姿勢出力率、最大reject連続時間地図外逸脱なし、有効率95%以上
精度開始点と終点の差、可能ならATE／RPE、既知地点の誤差用途に応じて0.2–0.5 m以内などを事前定義
リアルタイム性処理時間p50／p95／max、入力キュー、drop数10 Hz入力に遅延が累積しない
計算資源CPU平均／最大、RSS、GPU使用率、温度、クロック、消費電力熱定常後も20–30%の余裕
復旧性初期化時間、意図的な位置ずらしからの復帰、TF jump危険な誤リセットや大きなTF jumpなし

Jetsonでの測定例

# 1倍速・sim timeで同じrosbagを再生
ros2 bag play /path/to/bag --clock --rate 1.0

# JetsonのCPU・GPU・メモリ・温度・電力

# 対象プロセスのCPU・RSS・I/O

/usr/bin/time -v ros2 launch <package> <launch.py> ...

可視化を含む試験と、RViz・debug publishを止めた本番相当試験を分けて記録する。

10. 次に実施する手順

MOLAの地図軌跡が閉じているか確認開始点と終点、壁の二重化、帰着地点周辺をmm-viewer等で確認する。
MOLA公式順序で地図を再生成simplemap → mola-sm-lc-cli → sm2mmの順で、loop closure後の地図を作る。
前処理条件を揃えるmin/max range、自己領域、voxel、deskew、point timestamp、TF、初期姿勢をGLIM側と表にして比較する。
MOLA Localizationを再試験現在のMOLA 3.0系を使う場合は、IMU deskew、重力補正、StateEstimationSmootherの役割を分けてA/B試験する。
lidar_localization_ros2の基準値を測るNDT_OMPの精度、p95処理時間、CPU、メモリ、reject時刻を記録する。
同一地図でbackendを比較NDT_OMP → SMALL_GICP／SMALL_VGICP → v1.2密結合経路の順に比較する。
Jetsonで熱定常試験短時間だけでなく30–60分走らせ、温度・クロック低下後の処理遅延を確認する。
mapping用とlocalization用rosbagを分ける最終判定では別日または別走行のデータを用い、実運用に近い環境差を入れる。
採用ゲート： 「同一rosbag完走」→「別走行rosbag完走」→「Jetson 1倍速・熱定常で完走」→「実機Nav2走行」の順で進める。前段で地図外へ逸脱した方式は、計算が軽くても次段へ進めない。
