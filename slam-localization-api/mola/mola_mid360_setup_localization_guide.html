1. 全体像

1. 全体像

この版では、追加設定はすべてファイルとして同梱。 MOLA本体のYAML/launch/sourceを手で部分編集せず、mola_mid360_toolsを追加して実行する。

推奨フロー: Mid-360を人が持って高品質MAPを作成し、loop closureと後処理を済ませた固定MAPを、RealtimeまたはrosbagのLocalization専用モードで使用する。

Mid-360収録→LIO Mapping→.simplemap→Loop Closure→sm2mm→.mm→Localization only
.simplemapキーフレーム・姿勢・観測を保持。Loop closureなど後処理の元データ。
.mmLocalizationで照合するmetric map。今回のGICP用では localmap layerを使う。
Realtime実LiDAR/IMU topicをBridgeROS2で購読。wall clockを使用。
rosbaguse_sim_time:=True と ros2 bag play --clock をセットで使う。
今回確立したMid-360固有値: 近距離除去は MOLA_MINIMUM_RANGE_FILTER=0.1。sm2mm側の FilterByRange range_max も 0.1 m。3.0 mに戻すとロボット軌跡周辺の床まで大きく削る。

mola_shell()
{
    env -i \
        HOME="$HOME" USER="$USER" LOGNAME="$LOGNAME" \
        SHELL=/bin/bash TERM="$TERM" DISPLAY="$DISPLAY" \
        XAUTHORITY="$XAUTHORITY" \
        XDG_RUNTIME_DIR="$XDG_RUNTIME_DIR" \

        PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
        bash --noprofile --rcfile "$HOME/mola_ws/mola.bashrc" -i
}

7. 人などの動体除去

推奨: 添付済み sm2mm_mid360_dynamic_filter.yaml をpackageから自動参照する。 YAMLを作成・部分編集する必要はない。

  "$HOME/mola_maps/atr_out_Images/" \

YAMLを編集せずに調整

MODE用途
dynamic標準 0.70
dynamic-conservative0.60。床・壁を残しやすい
dynamic-aggressive0.75。人物を強めに除去
dynamic-debugstatic/dynamic layerを残して確認
ros2 run mola_mid360_tools build_metric_map INPUT.simplemap OUTPUT.mm EXTERNALS_DIR dynamic-debug

歩行者がLiDARの横を一緒に歩いた場合、通常の積算では人物がゴーストとして残る。Voxel occupancyを使い、繰り返し観測される高occupancy点をstatic、低occupancy点をdynamicとして分離する。

voxel resolutionまず0.15 m。0.10–0.20 mで調整。
occupancy thresholdまず0.7。人物が残る→0.75方向。壁/床まで消える→0.6方向。
動体除去の主要final_filters
final_filters:
  - class_name: FilterRemoveByVoxelOccupancy
    params:
      input_pointcloud_layer: "map"
      input_voxel_layer: "voxelmap"
      output_layer_static_objects: "static_map"
      output_layer_dynamic_objects: "dynamic_map"
      occupancy_threshold: 0.7

  - class_name: mp2p_icp_filters::FilterMLS
    params:
      input_pointcloud_layer: "static_map"
      output_pointcloud_layer: "mls"
      output_layer_class: "mrpt::maps::CGenericPointsMap"
      search_radius: 0.10
      polynomial_order: 2
      min_neighbors_for_fit: 10
      projection_method: FilterMLS::ProjectionMethod::SIMPLE
      upsampling_method: FilterMLS::UpsamplingMethod::NONE

  - class_name: mp2p_icp_filters::FilterMerge
    params:
      input_pointcloud_layer: "mls"
      target_layer: "localmap"
sm2mm \

9. Localization共通原則

  • start_mapping_enabled:=False — MAPを更新しない。
  • start_active:=False — 初期位置を与える前に誤マッチさせない。
  • publish_localization_following_rep105:=False — hand-held構成では map → livox_frame を直接Publish。
  • RVizの 2D Pose Estimate は /initialpose へ送られ、MOLAのrelocalizationに渡る。
  • 初期位置を与えた後、runtime parameter active: true で処理開始。

active ON/OFF

# 一時停止
ros2 service call /mola_runtime_param_set mola_msgs/srv/MolaRuntimeParamSet \
  "{parameters: \"mola::LidarOdometry:lidar_odom:\n  active: false\n\"}"

# 再開
ros2 service call /mola_runtime_param_set mola_msgs/srv/MolaRuntimeParamSet \
  "{parameters: \"mola::LidarOdometry:lidar_odom:\n  active: true\n\"}"
map frameが初期化前に存在しない場合: RVizで Fixed Frame = map を使うための表示補助として、別terminalからidentityの world → map static TFを出す。MOLAが出す map → livox_frame とは競合しない。
ros2 run tf2_ros static_transform_publisher \
  0 0 0 0 0 0 world map

12. Localizationが途中で失敗したときの手動復旧

推奨: 復旧時もYAMLやlaunchを編集しない。
# 1) ロボットまたはbagを停止
# 2) MOLA Localizationを停止
ros2 run mola_mid360_tools pause_localization

# 3) RViz: 2D Pose Estimateで正しい位置・向きを指定

# 4) 再開
ros2 run mola_mid360_tools resume_localization

できる。 MOLAの active をfalseにして入力処理を止め、RVizの2D Pose Estimateで再ローカリゼーションを要求し、その後activeを戻す。

Realtimeまずロボットを物理的/制御的に停止。LiDAR/IMUは流れ続けてよいがMOLAはinactiveで無視する。
rosbagSpaceでbag自体をpauseしてからMOLAもinactiveにするのが分かりやすい。

12.1 安全な復旧シーケンス

移動/Bag停止→active:false→2D Pose Estimate→active:true→移動/Bag再開

① MOLAを一時停止

ros2 service call /mola_runtime_param_set mola_msgs/srv/MolaRuntimeParamSet \
  "{parameters: \"mola::LidarOdometry:lidar_odom:\n  active: false\n\"}"

② RVizで2D Pose Estimate

地図上で現在の実位置をクリックし、LiDAR/ロボットが向いている方向へ矢印を向ける。BridgeROS2標準設定では /initialpose がrelocalizationへ渡される。

# メッセージが届いているか確認したいとき
ros2 topic echo /initialpose --once

③ MOLAを再開

ros2 service call /mola_runtime_param_set mola_msgs/srv/MolaRuntimeParamSet \
  "{parameters: \"mola::LidarOdometry:lidar_odom:\n  active: true\n\"}"

④ TFを確認してから移動再開

ros2 run tf2_ros tf2_echo map livox_frame
MOLA-LOの実装では relocalize_near_pose_pdf() が内部の initial_localization_done=false を設定し、指定poseとcovarianceを使って次iterationで再ローカリゼーションを強制する。そのため初回だけでなく、途中の再位置合わせにも利用できる。
Localization復旧で reset_state:true は原則使わない。 reset_stateは内部local map/simplemapまで初期化するトリガーなので、単なる位置ずれ修正には強すぎる。まずrelocalizationを使う。
プログラムからposeを送りたい場合

RVizを使わず、/initialpose に geometry_msgs/msg/PoseWithCovarianceStamped をpublishするか、MOLAの /relocalize_near_pose serviceを使用する。運用UIでは「停止」「現在位置指定」「再開」の3操作にまとめると扱いやすい。

13. TF設計

hand-held Mid-360

map
 └── livox_frame

publish_localization_following_rep105:=False。MOLAが直接 map → livox_frame を出す。

移動ロボット / Go2

map
 └── odom
      └── base_link
           └── livox_frame

Nav2等へつなぐ場合はREP-105構成を基本とし、ロボット側が odom → base_link、MOLAが map → odom を補正する。LiDARは実機取付TF base_link → livox_frame をstatic TF/URDFで与える。

14. Go2 / Nav2へ持っていくとき

MOLA_MINIMUM_RANGE_FILTER=0.1 \
ros2 launch mola_lidar_odometry ros2-lidar-odometry.launch.py \
  start_active:=False \
  start_mapping_enabled:=False \
  use_imu_for_lio:=True \
  lidar_topic_name:=/livox/lidar \
  imu_topic_name:=/livox/imu \
  mola_tf_base_link:=base_link \
  ignore_lidar_pose_from_tf:=False \
  ignore_imu_pose_from_tf:=False \
  publish_localization_following_rep105:=True \
  mola_initial_map_mm_file:="$HOME/mola_maps/atr_out_lc.mm"
前提: Go2側から妥当な odom → base_link が既に存在すること。REP-105ではMOLAはそのローカルodometryを置き換えず、map → odom を補正する。

17. Docker環境の作成・別PCへの配布

同梱済み: docker/Dockerfile、compose.yaml、短縮手順。2章のsource buildと本bundleのmola_mid360_toolsをイメージ内で構築する。

17.1 方針と前提

  • ホストにはDocker EngineとCompose pluginを導入しておく。
  • Livox UDPとROS 2 DDSのためLinux host networkを使用する。
  • MAPとrosbagはimageへ含めず、ホストの~/mola_maps／~/ros_bagsをvolume mountする。
  • GUIはX11 socketを共有する。Wayland専用環境やmacOS/Windowsでは別途X serverが必要。
CPUアーキテクチャ: amd64で通常buildしたimageはJetson（arm64）では動かない。配布先と同じアーキテクチャでbuildするか、buildxで対象を指定し、必ず実機でMOLAとGUIを検証する。

17.2 build

cd /path/to/ros2-materials/slam-localization-api/mola/docker
docker compose build
docker image inspect mola-mid360:humble

17.3 起動・確認

mkdir -p ~/mola_maps ~/ros_bags
xhost +local:docker  # GUIを使うLinuxホストだけ
docker compose run --rm mola

# コンテナ内
ros2 pkg prefix mola_lidar_odometry
ros2 pkg prefix mola_mid360_tools
ros2 run mola_mid360_tools check_mid360_topics

コンテナ内ではMAPを/data/maps、bagを/data/bagsとして指定する。終了後、必要ならホストでxhost -local:dockerを実行する。

17.4 USB等でオフライン導入

# 作成PC
docker save mola-mid360:humble | gzip > mola-mid360_humble.tar.gz
sha256sum mola-mid360_humble.tar.gz > mola-mid360_humble.tar.gz.sha256

# 2ファイルとdocker/compose.yamlを対象PCへコピー後
sha256sum -c mola-mid360_humble.tar.gz.sha256
gunzip -c mola-mid360_humble.tar.gz | docker load
docker compose -f compose.yaml run --rm mola

17.5 Registry経由で導入

# 作成PC（実際のregistry名へ置換）
docker tag mola-mid360:humble registry.example.com/robot/mola-mid360:humble
docker push registry.example.com/robot/mola-mid360:humble

# 対象PC
docker pull registry.example.com/robot/mola-mid360:humble
docker tag registry.example.com/robot/mola-mid360:humble mola-mid360:humble
docker compose -f compose.yaml run --rm mola
再現性と公開image: build日、各Git commit、CPU、image ID／RepoDigest、配布tarのSHA-256を保存する。既存の公開imageを参考・利用する場合は、提供元、ROS distro、アーキテクチャ、更新日を確認し、可変tagではなくdigestで固定して、同じbagとMAPで受入試験する。

17.6 実機前チェック

docker run --rm mola-mid360:humble \
  bash -lc 'ros2 pkg prefix mola_lidar_odometry && ros2 pkg prefix mola_mid360_tools'
docker compose config

続けて4章のtopic、13章のTF、Realtimeではwall clock、rosbagではuse_sim_timeと--clockを確認する。コンテナ化しても校正値やTF不整合は解消されない。
