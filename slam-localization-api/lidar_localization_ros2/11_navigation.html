11. Nav2ナビゲーション構成

オドメトリの必要性から理解する: 学習教材 第2章で、 TFの配信担当 → 積算する期間 → 計測とPublishの時系列 → Nav2の利用先 → 滑りの限界、の順に説明する。 以下の概要を確認してから、実機のインタフェースと起動手順へ進む。
手持ちLocalizationから変わる最大の点: ロボット運用ではMID-360そのものを base_frame にせず、 ロボット本体の base_link を基準にする。localizerは map → odom、ロボットのオドメトリ系は odom → base_link を担当する。

        ├── livox_frame     ← URDF / robot_state_publisher / static TF

11.0 なぜodomを挟むのか、処理を追って理解する

odomを挟んでもmap上の自己位置はジャンプし得る。 地図上の位置を訂正する map → odom と、連続した移動を表す odom → base_link を分け、局所観測と遠方の経路を両立させる。 odom はロボットに固定された座標ではない。自分相対の基準は base_link である。

担当と周期を分ける

担当配信する情報周期の考え方
車輪・脚Odom、EKF、LIO、VIOのいずれかodom → base_link とOdometry例: 50 Hz。センサーと状態推定器の設定で決まる
lidar_localization_ros2地図上の姿勢Topic、Nav2モードでは map → odom地図照合は点群入力と採用条件に依存。予測や再配信の頻度とは区別する
Nav2 Controller速度指令 /cmd_vel例: 20 Hz。controller_frequency などの設定で決まる

周期は説明用で、必須値ではない。EKFがTFを出す場合は、車輪側の同じTF配信を止める。 Odometry Topicを出すだけではTFは自動生成されない。

「いつからの移動か」と、計測・Publishの時間差

odom → base_link は通常、起動・初期化時に定めた原点に対する累積位置・姿勢であり、 前回のLiDAR照合からの変位だけではない。LiDARの推定が届くたびにリセットしない。 前回からの移動量が必要なら、2時刻のオドメトリ姿勢から求める。

回転のない直線運動で、10.00秒の点群を処理し、10.06秒に結果が得られた例を考える。

10.00秒: odom位置は5.00 m。LiDARの地図照合を開始
10.02秒: odom位置は5.02 m。地図照合は計算中
10.04秒: odom位置は5.04 m。地図照合は計算中
10.06秒: odom位置は5.06 m。
         「10.00秒のmap位置は104.00 m」と判明

同じ計測時刻で補正を計算:
map → odom = 104.00 - 5.00 = 99.00 m

補正を保持して、その後の移動を反映:
map位置(10.06) = 99.00 + 5.06 = 104.06 m
              = 104.00 + (5.06 - 5.00)

「つながるように計算」とは、同時刻のTFを合成した姿勢を地図照合結果へ一致させること。 Publish時刻の最新odomを引くと、計算中の移動まで誤って補正に入る。 回転を含む式は C = M(ts) × inverse(O(ts))、その後の姿勢は C × O(t) となる。

実際に10.06秒のTFを参照するには、必要な辺がその時刻まで利用できなければならない。 TFは古い動的変換を無期限に未来へ延長しない。再配信・有効時刻はノードの実装に従い、 Nav2は利用可能なTFと許容遅延に従う。オドメトリ、地図照合、Nav2制御は独立したループである。

Nav2のどこで使われるか

用途典型的な参照先効果
大域経路計画map → base_link、地図、目的地見えない遠方の目的地へ向かう経路を作る
局所障害物の保持観測時刻の odom → base_link → sensor地図補正だけで過去と現在の局所観測がずれるのを防ぐ
経路追従局所基準の姿勢・障害物と、TFで変換したmap上の経路近傍の回避と地図上の訂正を組み合わせる
現在速度odom_topic に指定したOdometryの twist地図上のジャンプを実際の急加速と取り違えにくい

例えば静止中にmap上の位置が105 mから104 mへ訂正されても、odom上の自分が5 m、前方2 mの壁が7 mという関係は保てる。 map上の経路点は新しい補正でodomへ変換するため、経路に対する距離は訂正される。 現在速度が連続でも指令の急変は起こり得るので、Controllerの加減速制限やVelocity Smootherも設定する。

滑りはodomを設けるだけでは直らない

車輪が回らず機体だけが壁へ0.5 m滑ると、車輪odomは「移動なし」と判断し、 壁までの距離だけが2 mから1.5 mへ変わる。LiDAR地図照合でmap上の位置を直せても、 odomで保持した過去の障害物や、見逃した移動履歴が自動で直るわけではない。

局所地図を観測・クリア・減衰などで更新するとともに、滑りを観測できるLIO・VIO・IMUなどを適切に選択・融合する。 IMU単独の長時間の位置積分や、どのセンサーにも見えていない移動をEKFで復元することは期待しない。 連続性と正確さは別である。

実装の読み方、確認コマンド、理解度確認は 学習教材 2.11を参照。 導入の参考: 赤井直紀氏のオドメトリフレーム（/odom）とは何か。

11.2 3Dマップと2Dマップは両方使う

lidar_localization_ros2 には3D PCDからNav2用の粗い2D mapを生成する generate_occupancy_map_from_pcd.py が含まれている。

mkdir -p ~/ros2_ws/src/lidar_localization_ros2/map/nav2

ros2 run lidar_localization_ros2 generate_occupancy_map_from_pcd.py \
  --pcd ~/ros2_ws/src/lidar_localization_ros2/map/atr_out_points.pcd \
  --output-dir ~/ros2_ws/src/lidar_localization_ros2/map/nav2 \
  --map-name atr_nav2 \
  --resolution 0.10

map/nav2/

自動生成した2D mapは最終成果物ではなくスタート地点。 床・壁・ガラス・段差などが誤判定されることがあるため、Nav2運用前に画像を確認し、 必要ならPGM/PNGを編集する。

11.4 ロボット側を先に完成させる

Step 1 — base_link → LiDAR / IMU

本番ではstatic_transform_publisherを増やすより、URDFにセンサ取付位置を記述して robot_state_publisher から出す構成を推奨する。

ros2 run tf2_ros tf2_echo base_link livox_frame
ros2 run tf2_ros tf2_echo base_link livox_imu_frame

Step 2 — odometry

ros2 topic hz /odom
ros2 topic echo /odom --once
ros2 run tf2_ros tf2_echo odom base_link

停止中に大きく飛ばず、移動時に滑らかに変化することを確認する。 長時間のdriftは許容される。globalなdrift補正は map → odom が担当する。

Step 3 — cmd_vel adapter

Nav2 /cmd_vel
   ↓ geometry_msgs/msg/Twist
自作 adapter node
   ↓
ロボットSDK / 歩行速度API

初回はNav2を使わず、手動で小さな /cmd_vel を送り、 前進・後退・旋回・停止が期待通りになることを単体試験する。

11.5 LocalizationをNav2用TFモードへ変更

手持ち版:

map → livox_frame
enable_map_odom_tf = false
base_frame_id = livox_frame

Nav2版:

map → odom → base_link → livox_frame

enable_map_odom_tf = true
global_frame_id = map
odom_frame_id = odom
base_frame_id = base_link
TFの二重Publishは禁止。 map → odom はlocalizerだけ、 odom → base_link はロボットodometryだけ、 base_link → sensor はURDF/robot_state_publisher等の1系統だけがPublishする。

11.6 現行リポジトリのNav2統合Launch

リポジトリには nav2_navigation.launch.py があり、 localizer、Nav2 map_server、Nav2 navigation stackをまとめて起動できる。 PointCloud2 topic、odom topic、frame IDもlaunch時に書き換えられる。

ロボット側の /odom とTFが完成した後の例:

source /opt/ros/humble/setup.bash
source ~/livox_ws/install/setup.bash
source ~/ros2_ws/install/setup.bash

ros2 launch lidar_localization_ros2 nav2_navigation.launch.py \
  pcd_map_path:=$HOME/ros2_ws/src/lidar_localization_ros2/map/atr_out_points.pcd \
  map_yaml:=$HOME/ros2_ws/src/lidar_localization_ros2/map/nav2/atr_nav2.yaml \
  cloud_topic:=/livox/lidar \
  pointcloud_topic:=/livox/lidar \
  imu_topic:=/livox/imu \
  odom_topic:=/odom \
  global_frame_id:=map \
  odom_frame_id:=odom \
  base_frame_id:=base_link \
  lidar_frame_id:=livox_frame \
  publish_lidar_tf:=false \
  publish_imu_tf:=false \
  localizer_enable_map_odom_tf:=true \
  use_sim_time:=false
publish_lidar_tf:=false / publish_imu_tf:=false は、 URDF側ですでにsensor TFを出している前提。URDFに無い場合だけlaunch側でPublishし、 実測extrinsicsを設定する。

robot_radius / footprint

同梱のNav2 presetは初期値として円形 robot_radius を使う。 実際の4足・ヒューマノイドでは外形寸法に合わせて値を設定するか、 専用Nav2 paramsを作ってpolygon footprintへ変更する。

11.7 MID-360 IMUをNav2統合時も使うための注意

現行mainの注意点: nav2_navigation.launch.py は内部の nav2_lidar_localization.launch.py に use_imu_preintegration を渡していない。 内部launch側のdefaultが false なので、 統合Nav2起動ではYAML側でtrueでも上書きされる。

この資料には最小パッチを同梱:

fix/nav2_navigation_mid360_imu.patch

適用例:

cd ~/ros2_ws/src/lidar_localization_ros2

cp launch/nav2_navigation.launch.py \
   launch/nav2_navigation.launch.py.original

patch -p0 < /path/to/guide/fix/nav2_navigation_mid360_imu.patch

cd ~/ros2_ws
colcon build --symlink-install --packages-select lidar_localization_ros2
source install/setup.bash

パッチ後は:

ros2 launch lidar_localization_ros2 nav2_navigation.launch.py \
  ... \
  use_imu_preintegration:=true \
  imu_preintegration_use_base_frame_transform:=true

imu_preintegration_use_base_frame_transform:=true を使う場合は base_link → livox_imu_frame が正しく存在する必要がある。
