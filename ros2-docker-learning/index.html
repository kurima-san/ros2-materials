STEP 01

ROS 2開発でDockerを使う理由

Dockerが解決する問題を理解してから、コマンドへ進みます。

Dockerを使わない場合

  • PCごとにROS 2やライブラリの状態が違う
  • pipやaptの追加で環境が複雑になる
  • 別PCへの移行手順が長くなる
  • 開発環境と実機環境の差が大きくなる

Dockerを使う場合

  • 必要なソフトを設定ファイルへ記録できる
  • 環境を作り直しやすい
  • プロジェクトごとに環境を分けられる
  • 開発PCからUbuntu・Jetsonへ移しやすい
Dockerの役割：プログラムそのものだけでなく、そのプログラムを動かすOS環境と依存ライブラリもまとめて管理します。

ImageDockerfileから作られる、起動前の完成済み環境です。
ContainerImageを実際に起動したものです。ROS 2プログラムはこの中で動きます。
Compose複数のContainer、ネットワーク、フォルダー共有、ポート、起動方法をまとめる仕組みです。

Composeはこの流れの外側で、複数のContainerをまとめて管理します。

重要：ComposeはContainerの種類ではありません。Containerの構成と起動方法をまとめる管理機能です。

STEP 04

Docker単体の基本操作を順番に理解する

Composeを使う前に、Image取得・Image作成・Container起動の違いを学びます。

操作役割結果
docker pull公開済みImageを取得するImageがPCへ保存される
docker buildDockerfileからImageを作る自分のImageが作られる
docker runImageからContainerを作って起動するプログラムが実行される
pull
Imageを取得
または
build
Imageを作成
→
run
Containerを作成・起動
最初の動作確認
docker run --rm hello-world

必要なImageがPCにない場合は、Dockerが自動的に取得してからContainerを起動します。

単体コマンドをもう少し試す
docker pull ubuntu:24.04
docker run --rm -it ubuntu:24.04 bash

exitで一時Containerを終了します。

Container・Imageを安全に削除して作り直す

「再インストール」は、まずContainerを停止・削除し、必要ならImageを削除してから、pullまたはbuildし直す順番で行います。Imageを削除しても、bind mountしたPC側のソースや設定は削除されません。

目的操作残るもの
Containerだけ作り直すdocker rm後にdocker runImage
公開Imageを入れ直すdocker image rm後にdocker pullPC側データ
自作Imageを完全再builddocker image rm後にdocker build --no-cacheDockerfile・PC側データ
Docker単体：公開Imageを入れ直す
# 1. 対象Imageを使うContainerを確認
docker ps -a --filter ancestor=ubuntu:24.04

# 2. 表示されたContainerを停止・削除
docker stop CONTAINER_ID
docker rm CONTAINER_ID

# 3. Imageを削除し、もう一度取得
docker image rm ubuntu:24.04
docker pull ubuntu:24.04

# 4. 再起動して確認
docker run --rm -it ubuntu:24.04 bash
Compose：ContainerとImageを作り直す
# compose.yamlがあるディレクトリで実行
docker compose down --remove-orphans
docker compose images

# Composeが参照するImageを削除する場合
docker image rm IMAGE_NAME:TAG

# キャッシュを使わず、base Imageも更新確認して再build
docker compose build --no-cache --pull
docker compose up -d
docker compose ps
削除範囲を確認：docker compose downは通常named volumeを残します。down -vはnamed volumeも削除するため、DBやbagなど必要なデータがないことを確認してから使います。docker system prune -aは他プロジェクトの未使用Imageも対象になるため、最初の対処には使いません。
Imageを削除できない時の確認順
  1. docker ps -a --filter ancestor=IMAGE_NAME:TAGで参照中のContainerを探す。
  2. docker stopとdocker rmでそのContainerだけを削除する。
  3. docker image rm IMAGE_NAME:TAGを再実行する。
  4. docker image lsとdocker image inspect IMAGE_NAME:TAGで状態を確認する。

docker image rm -fは参照関係を理解した場合だけ使用します。

STEP 05

Dockerfileで開発環境の作り方を記録する

Dockerfileは、ROS 2環境を再現するための手順書です。

項目意味使われる時
FROM土台にする環境Imageを作る時
RUNソフトの追加やビルドImageを作る時
CMD起動時の標準動作Containerを起動する時
ENTRYPOINT起動時に必ず行う準備Containerを起動する時
最小のDockerfile
FROM ros:lyrical-ros-base
RUN apt-get update && apt-get install -y python3-colcon-common-extensions
CMD ["bash"]

このファイルからImageを作る時だけ、次の操作を使います。

docker build -t my-ros2-dev .
暗記する必要はありません。最初は「RUNはImage作成時」「CMDはContainer起動時」と区別できれば十分です。

STEP 06

Composeで開発環境全体をまとめる

Containerごとに長い起動設定を書く代わりに、YAMLへ構成を保存します。

Composeに書くもの

  • 使用するImageまたはDockerfile
  • 起動するContainerの単位
  • 共有するプロジェクトフォルダー
  • ブラウザや外部PCへ公開するポート
  • 環境変数と起動時のプログラム

本教材の開発構成

  • desktop：GUIと開発Terminal
  • fake_lidar：疑似センサー
  • monitor：受信確認
  • 3つをつなぐ共通ネットワーク
簡略化したcompose.dev.yaml
services:
  desktop:
    build:
      dockerfile: docker/Dockerfile.dev
    volumes:
      - .:/workspace
    ports:
      - "127.0.0.1:6080:6080"

  fake_lidar:
    build:
      dockerfile: docker/Dockerfile.runtime
Composeの目的：起動のたびに設定を考えるのではなく、同じ開発環境を何度でも再現できるように保存することです。

STEP 07

Composeで環境を起動・確認・操作・終了する

ここで初めて、up・ps・exec・logs・downを学びます。

操作何をするか対象
upYAMLを読み、必要なサービスを作って起動する通常はYAML内のサービス群
ps起動状態を確認するサービス群
exec desktop bash起動中のdesktop内でbashを開くdesktop 1つ
logs実行中の出力を確認するサービス群または指定サービス
down停止し、Composeが作ったContainerとNetworkを片付けるCompose環境全体
開発環境の基本操作
# 1. Imageを必要に応じて作り、サービス群を裏で起動
docker compose -f compose.dev.yaml up -d --build

# 2. 起動状態を確認
docker compose -f compose.dev.yaml ps

# 3. 起動済みdesktop 1つの中へ入る
docker compose -f compose.dev.yaml exec desktop bash

# 4. Container内から出た後、環境を終了
docker compose -f compose.dev.yaml down

upはYAMLからbuildする操作？

upの中心的な役割は、サービスを作成して起動することです。Imageを起動前に作る指定は、末尾の--buildです。

exec desktop bashは全Containerを実行する？

いいえ。すでに起動しているdesktopという1サービスを選び、その中でbashを開きます。全サービスの起動はupが行います。

補助的なCompose操作
configYAMLの内容を検査する
stopContainerを残したまま停止する
start停止済みContainerを再開する
buildImageだけを作る

STEP 08

開発用環境と完成版環境を分ける

開発中に必要な機能と、実行時に必要な機能は異なります。

compose.dev.yaml

  • GUIとTerminalを含む
  • ソースをPC側から共有する
  • 何度も編集・ビルド・試験する
  • 疑似センサーを別サービスで動かす

compose.runtime.yaml

  • GUIや編集ツールを省く
  • 完成済みプログラムを含める
  • 起動時にROS 2システムを自動実行する
  • 運用先PCでは基本的に編集しない
比較項目開発用完成版
目的編集・確認安定実行
Desktopあり通常なし
ソース共有ありなし
起動後の操作開発者が操作プログラムを自動起動

STEP 13

ROS 2のContainer間通信と外部ロボット通信

まず同じPC内で確認し、その後にLAN上の実機へ進みます。

最初に確認する範囲

  • fake_lidarがデータを送る
  • monitorがデータを受ける
  • desktopのRViz2が表示する
  • 各サービスのROS_DOMAIN_IDを同じにする

後から確認する範囲

  • LAN上のロボットや別PC
  • Wi-FiやVPNを越える通信
  • 複数ネットワーク機器の選択
  • Discovery Serverなどの追加設定
学習時の目標：同じCompose内でROS 2ノード同士が通信できれば、基本部分は成功です。
外部ロボット通信の用語

ROS 2はDDSを使い、相手を見つけるためにUDPやmulticastを利用します。Windows＋WSL＋Docker Desktopではネットワーク変換が入るため、Ubuntuネイティブと同じ動作にならない場合があります。

services:
  robot_system:
    network_mode: host
    environment:
      ROS_DOMAIN_ID: "42"

network_mode: hostは主にUbuntuネイティブやJetsonの実機確認で使います。

STEP 17

ROS 2 × Docker開発の最終ワークフロー

普段の開発から実機運用までの順番を1つにつなげます。

  1. DockerfileでROS 2と依存ライブラリを定義する
  2. compose.dev.yamlでGUI・ソース共有・疑似センサーを定義する
  3. 開発環境を起動し、Container内で編集・ビルド・試験する
  4. 同じCompose内でROS 2通信を確認する
  5. compose.runtime.yamlで完成版の自動起動を定義する
  6. UbuntuまたはJetsonへImageとCompose設定を移す
  7. 外部通信、USB、GPU、再起動を実機確認する
my_robot/ ├── src/ # ROS 2ソース ├── docker/ │ ├── Dockerfile.dev # GUI付き開発環境 │ └── Dockerfile.runtime # 完成版環境 ├── compose.dev.yaml # 開発用設定 ├── compose.runtime.yaml # 運用用設定 ├── start-dev.sh / .bat # 開発環境を起動 ├── open-terminal.sh / .bat # Container内Terminalを開く └── stop-dev.sh / .bat # 開発環境を終了
  • Dockerfile、Image、Container、Composeの関係を説明できる。
  • Docker単体の操作とComposeの操作を区別できる。
  • 開発用と完成版の設定を分けられる。
  • Container内でROS 2をビルド・実行できる。
  • Dockerの通信とROS 2通信を段階的に確認できる。
  • WSL、Ubuntu、Jetsonの役割を選べる。
