STEP 00

結論：Dockerfile・Compose・ROS 2 launchを分担する

開発環境の再現、開発中の操作、完成版の一括起動を別の層として設計します.

目標は、開発時にはブラウザでデスクトップを開き、完成後は1コマンドでROS 2システムを起動できる構成です。
Dockerfile
OS、ROS 2、apt/pip、開発ツール
→
再現可能なイメージを作る
Compose
mount、network、GPU、USB、起動サービス
→
複数コンテナを1コマンドで管理する
ROS 2 launch
ノード、parameter、remap、namespace
→
ロボットアプリのノード群を起動する

開発用

ソースをbind mountし、コンテナを常駐させて反復ビルドします。標準サンプルはXFCE＋noVNCを使います。

実行用

ソースをイメージ内でビルドし、install成果物だけを持つruntime imageを作ります。

通信

同一Compose、ホスト接続、外部PC、ROS 2 DDSを別々に理解します。

STEP 01

Dockerとは：ImageとContainerを区別する

DockerはLinuxカーネルを共有しながら、プロセス・ファイルシステム・ネットワークを隔離します.

Dockerfile
→
docker build
→
Image
→
Container
Dockerfileイメージを作る手順書です。
ImageROS 2と依存関係を含む読み取り専用テンプレートです。
Containerイメージから起動したプロセス環境です。削除可能な作業環境として扱います。
RegistryDocker Hubや社内Registryなど、イメージの保管場所です。
Compose複数コンテナ、mount、network、環境変数をYAMLでまとめます。
重要：ソースコードをコンテナ内だけに作らないでください。開発中はbind mount、成果物やデータはvolumeを使い、コンテナを消しても残るようにします。

STEP 02

Windows＋WSL 2とUbuntuへDockerを導入する

WindowsはDocker Desktop＋WSL Integration、UbuntuネイティブはDocker Engineが基本です.

  1. WSL 2 Ubuntuを用意する。
  2. Docker Desktopを導入する。
  3. Settings → Resources → WSL IntegrationでUbuntuを有効にする。
  4. プロジェクトは原則としてWSL側の ~/workspace に置く。
PowerShell
wsl --update
wsl -l -v
wsl --set-default-version 2

Docker公式手順でDocker EngineとCompose pluginを導入します。古い docker-compose ではなく docker compose を使います。

共通確認
docker version
docker compose version
docker run --rm hello-world

WSLでWindows側の C:\... をmountするより、WSL Linuxファイルシステムの /home/... にソースを置く方が、一般にbind mountの性能とファイル監視に有利です。

STEP 03

最初のコンテナを対話的に使う

コンテナは仮想PCではなく、指定したメインプロセスが終了すると停止する環境です.

Terminal
docker run --rm -it ros:lyrical-ros-base bash
printenv ROS_DISTRO
ros2 --help
exit
オプション意味
--rm終了後にコンテナを削除
-it対話端末を割り当てる
ros:...起動元のイメージ
bash今回のメインプロセス

STEP 04

RUN・CMD・ENTRYPOINTを正しく使う

イメージ作成時とコンテナ起動時のコマンドを分けます。ここでの起動時とはDocker Engine自体ではなく、containerをstartする時です。

Dockerfile
ARG ROS_DISTRO=lyrical
FROM ros:${ROS_DISTRO}-ros-base

# build時に一度だけ実行
RUN apt-get update && apt-get install -y git

# 起動時に必ず通す初期化
ENTRYPOINT ["/ros_entrypoint.sh"]

# 起動時のデフォルト。docker runやComposeで上書き可能
CMD ["bash"]
命令実行時点ROS 2での用途
RUNdocker buildapt、pip、colcon build
ENTRYPOINT毎回のcontainer起動時ROS環境のsource
CMDcontainer起動時デフォルトのlaunchまたはbash
Compose commandcontainer起動時DockerfileのCMDを上書き
理解：完成版で「起動コマンドを1つにまとめる」とは、長いシェルコマンドへ全部詰めることではありません。最上位を docker compose up にし、内部でComposeとROS 2 launchへ分担させます。

STEP 05

Docker内で開発する：ソースをbind mountする

編集ファイルはホスト／WSLに残し、compilerやROS 2 CLIをコンテナ側へ統一します.

compose.dev.yaml
services:
  dev:
    build:
      context: .
      dockerfile: docker/Dockerfile.dev
    volumes:
      - .:/workspace
    working_dir: /workspace
    stdin_open: true
    tty: true
    command: sleep infinity
開発ループ
docker compose -f compose.dev.yaml up -d --build
docker compose -f compose.dev.yaml exec dev bash

colcon build --symlink-install
source install/setup.bash
ros2 run my_package my_node

--symlink-installはPythonやresourceファイルの反復開発に便利です。C++を変更した場合は再ビルドします。

STEP 06

標準開発環境：ブラウザでROS 2デスクトップを表示する

同梱サンプルはXFCE、TigerVNC、noVNC、RViz2をコンテナへ入れ、ブラウザだけでGUIを使えます.

この教材のデフォルト：start-dev.sh または start-dev.bat で、noVNCデスクトップ、疑似LiDAR、監視ノードを起動します。RViz2も自動起動します。
WSL / Ubuntu
cd examples/01_wsl_ubuntu_desktop
./start-dev.sh
Windows
examples\01_wsl_ubuntu_desktop\start-dev.bat

ブラウザURL：http://127.0.0.1:6080/vnc.html?autoconnect=1&resize=scale、初期パスワード：ros2

用途：noVNCは開発と学習向けです。ロボット本番環境ではGUIを外し、runtime imageを使います。

STEP 07

ROS 2ワークスペースをコンテナ内で反復開発する

依存解決、ビルド、source、実行、テストを一定の順番にします.

Container terminal
cd /workspace
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash
colcon test
colcon test-result --verbose
ros2 launch docker_ros2_lab lab.launch.py

同梱パッケージは /scan に疑似LaserScanをpublishし、最短距離をmonitorします。物理LiDARがなくてもtopic、QoS、RViz2の学習ができます。

STEP 08

開発版と完成版を分ける

開発版はtoolとmountを優先し、完成版は小ささ・再現性・自動起動を優先します.

compose.dev.yaml

  • ソースをbind mount
  • noVNCデスクトップ
  • debugger、editor、terminal
  • コンテナを常駐

compose.runtime.yaml

  • build済みinstallを含む
  • ソースmountなし
  • ROS 2 launchをCMDにする
  • restart policyを設定可能
開発
docker compose -f compose.dev.yaml up --build
完成版
docker compose -f compose.runtime.yaml up --build

STEP 09

完成版を1コマンド起動にする

Composeを外部インターフェース、ROS 2 launchを内部インターフェースとして扱います.

Dockerfile.runtime
FROM ros:${ROS_DISTRO}-ros-base AS builder
COPY src /workspace/src
RUN . /opt/ros/${ROS_DISTRO}/setup.sh && colcon build --merge-install

FROM ros:${ROS_DISTRO}-ros-base AS runtime
COPY --from=builder /workspace/install /workspace/install
ENTRYPOINT ["/entrypoint.sh"]
CMD ["ros2", "launch", "docker_ros2_lab", "lab.launch.py"]
利用者が実行するコマンド
docker compose -f compose.runtime.yaml up --build
# バックグラウンド
docker compose -f compose.runtime.yaml up -d --build
# ログ
docker compose -f compose.runtime.yaml logs -f
# 終了
docker compose -f compose.runtime.yaml down

STEP 10

Docker通信を4方向に分ける

container間、hostからcontainer、containerからhost、外部PCからcontainerを混同しないようにします.

方向基本設定接続先の例
container → container同じCompose networkserver:8000
host → containerports127.0.0.1:8080
container → hosthost.docker.internalhost.docker.internal:8000
外部PC → containerport publish＋host firewallHOST_IP:8080
Compose
services:
  web:
    ports:
      - "127.0.0.1:8080:80"
  client:
    extra_hosts:
      - "host.docker.internal:host-gateway"  # Linux Engine用
サービス名DNS：同じCompose projectの通常のTCP/UDP通信では、IP固定ではなくサービス名を使います。

STEP 11

ROS 2 DDS通信をDockerで扱う

ROS 2は固定ポート1本ではなく、DDS Discovery、UDP、multicast、domain、RMWが関係します.

  • 通信させるノードで ROS_DOMAIN_ID をそろえる。
  • RMW_IMPLEMENTATION とDDS設定を把握する。
  • 同じCompose bridge内でまず確認する。
  • 外部ロボットとの通信はUbuntuネイティブのhost networkから試す。
  • multicastが通らない場合はDiscovery Serverやexplicit peersを検討する。
Ubuntuネイティブ向け
services:
  robot_system:
    network_mode: host
    ipc: host
    environment:
      ROS_DOMAIN_ID: "42"
multicast確認
# PC A
ros2 multicast receive
# PC B
ros2 multicast send
Docker Desktopの注意：Windows＋WSL 2ではLinuxコンテナがDocker Desktopの仮想化・NAT層の内側にあります。同一PCの学習には便利ですが、LAN上の実機DDS通信はUbuntuネイティブと同じ挙動にならないことがあります。

READMEを開く

STEP 13

WSL＋Jetson想定：実機なしでARM64開発するサンプル

Docker Buildx/QEMUでlinux/arm64イメージをbuild・実行し、CPU側のROS 2処理と依存関係を先に検証します.

02_wsl_jetson_crossdev

Jetsonと同じARM64向けにROS 2 packageをbuildし、疑似センサーとplatform情報を実行します。

READMEを開く

実機なしで確認可能

  • arm64 buildが通るか
  • 依存packageのarm64 availability
  • ROS 2 nodeの基本動作
  • fake sensorの処理
WSL / Docker Desktop
cd examples/02_wsl_jetson_crossdev
./run-jetson-sim.sh
確認できないもの：CUDA、TensorRT、Jetson camera、NVENC/NVDEC、GPIO、実機性能、JetPack/L4Tドライバ整合性はJetson実機が必要です。ARM64 emulationは機能確認用で、性能評価には使えません。

STEP 14

Ubuntuネイティブで実機ネットワークへ接続する

センサー、GPU、DDS、低レイヤのネットワークを扱う最終確認環境です.

同梱サンプル
cd examples/03_ubuntu_native_network
./start-host-network.sh

このサンプルは network_mode: host と ipc: host を使います。Fast DDSのshared memoryをcontainer間で使う場合、networkとIPCを同時に共有する構成が必要になることがあります。

Linux専用：Docker Desktopのhost networkにはLinuxネイティブと異なる制約があります。実機DDSの最終評価はUbuntuネイティブまたはJetsonで行います。

STEP 15

Jetsonへ配布する：ARM64とJetPackを分けて考える

通常のUbuntu ARM64コンテナと、Jetson GPU対応コンテナは同じではありません.

CPU側ROS 2

公式ROS imageはamd64とarm64を提供しています。Buildxでmulti-platform imageを作れます。

Jetson GPU側

対象JetPack／Jetson Linuxと互換性のあるNVIDIA image、container runtime、host driverが必要です。

multi-platform build
docker buildx build   --platform linux/amd64,linux/arm64   -t registry.example.com/my-robot:1.0   --push .

同梱の Dockerfile.jetson-gpu.template は、対象機体のJetPackに合う JETSON_BASE_IMAGE を明示して使う雛形です。最新タグを固定で決め打ちしていません。

STEP 16

カメラ・LiDAR・シリアル・GPUを渡す

kernel driverと物理認識はhost、ユーザー空間SDKとROS nodeはcontainerへ置きます.

Compose例
services:
  camera:
    devices:
      - /dev/video0:/dev/video0
    group_add:
      - video
  serial_driver:
    devices:
      - /dev/ttyUSB0:/dev/ttyUSB0
  perception:
    gpus: all
  • udev ruleはhostへ置く。
  • 最初から privileged: true にせず、必要なdeviceだけ渡す。
  • NVIDIA driverはhost、NVIDIA Container Toolkitと対応libraryを使う。
  • WSLのUSBはusbipd等の追加経路が必要になるため、実機試験はUbuntuネイティブの方が単純です。

STEP 17

完成判定と推奨プロジェクト構成

開発者が変わってもREADMEと1コマンドで再現できることを完成条件にします.

my_robot/ ├── src/ ├── docker/ │ ├── Dockerfile.dev │ ├── Dockerfile.runtime │ └── entrypoint.sh ├── compose.dev.yaml ├── compose.runtime.yaml ├── compose.ubuntu-host.yaml ├── .devcontainer/ ├── config/ └── README.md
  • 新しいPCでREADMEだけを見てbuildできる。
  • 開発環境はブラウザまたはDev Containersで入れる。
  • 完成版は docker compose up で起動する。
  • source、config、rosbag、logがcontainer削除後も残る。
  • amd64とarm64のbuildをCIまたはBuildxで確認する。
  • 実機DDS、GPU、USBはUbuntu／Jetsonで最終確認する。
